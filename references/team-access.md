# Shared engineer access

Use this checklist when MCP query access is selected, either during the [initial installation](install.md) or later. It brings the existing authentication and routing steps together; keep the same saved values file and preserve existing configuration. The unpinned change procedure can upgrade the chart and application; review that effect before applying it.

## Prepare once

Collect the intended users and coding agents, approved private or public HTTPS hostname, DNS and certificate owners, human identity provider, and the installed runner's Secret references. The standard installation manages the runner's machine login; do not request another provider or client secret solely for the runner. Check the [native-auth release prerequisite](upgrading.md#native-machine-authentication-release-prerequisite) before using that path. Keep credentials out of chat and use [Secret references](credentials.md#use-existing-kubernetes-secrets).

| Step | Action | Completion evidence |
| --- | --- | --- |
| 1. Choose reachability | Prefer the team's approved [private route](private-access.md#team-access). Use [public MCP Ingress](public-mcp-ingress.md) only when selected. Prepare the hostname and TLS before opening shared access. | The intended users' devices and browsers can reach the chosen HTTPS hostname; unrelated clients remain excluded by the selected access policy. |
| 2. Preserve machine authentication | Follow the [runner machine-login guide](alert-investigations.md#prepare-runner-credentials-when-mcp-authentication-is-enabled). Keep `mcp.auth.enabled: true`. For the standard local target, the installer manages the native client and Secret with `mcp.auth.provider: none`. Preserve any selected external credentials and target settings. | The runner retains its installed identity and credential reference; no new external credential provider is needed for the standard runner. |
| 3. Configure human sign-in | Use the supported credential login or add [Google Workspace SAML](google-saml.md) or [Okta SAML](okta-saml.md). Set `mcp.auth.baseUrl` to the chosen HTTPS origin and match the provider's redirects. Human login does not replace the runner's machine login. | Identity-provider application and Tokonoma settings agree on hostname, redirects, and selected users. |
| 4. Apply the settings | For a new release, include authentication and routing in the [installation values](install.md#3-install). For an existing release, follow [configuration preservation](upgrading.md#before-changing-configuration). Keep the read-only local UI on a localhost port-forward; it needs no sign-in or copied machine credential. | Workloads are healthy; OAuth metadata returns `200` and unauthenticated `/mcp` returns `401`, as checked in [OAuth verification](oauth.md#3-deploy-and-verify). |
| 5. Verify both callers | Connect a [coding agent](coding-agents.md#use-a-public-endpoint) to the shared HTTPS `/mcp` endpoint and complete real login. Confirm the runner authenticates to its private MCP and can discover its tools. With application telemetry available, repeat [monitoring verification](agentic-monitoring.md#verify-monitoring) and an approved [investigation test](alert-investigations.md#check-it-works). | Human login completes an authenticated tool listing. Read an existing authorized record only when one is available, or run the optional [memory smoke test](install.md#connect-and-confirm-memory-access) when approved; the runner connects to its MCP without authentication errors. If customer data is not connected yet, record monitoring and investigation checks as pending, finish access setup, and provide the collector example. |

The coding-agent guide's HTTPS login steps also apply to private HTTPS routes reachable by the client and browser. A successful human login alone does not verify runner authentication, and successful tool discovery alone does not verify customer telemetry. Keep the route restricted and report the blocker if either caller fails; do not disable authentication to complete the checklist.

Record the final hostname, provider, Secret names, versions, and verification results in the installation report, without secret values. Alert webhooks use separate receiver tokens and may use a [separate route](private-access.md#slack-and-webhooks); do not expose MCP just to receive alerts.
